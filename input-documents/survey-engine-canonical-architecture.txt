Survey Engine – Canonical Architecture and Core Data Contracts

Purpose

This specification consolidates the survey engine architecture before reporting. It defines the canonical template, instance, submission, URL encoding, rule/scoring model, publication validation, and result model.

1. Architectural Model

The engine distinguishes five concepts:

SurveyTemplate
SurveyInstance
SurveyResponse
SurveySubmission
SurveyGroup

- SurveyTemplate — immutable published definition; owns meaning.
- SurveyInstance — one concrete occurrence of a survey; owns identity/context.
- SurveyResponse — logical decoded answers used by the engine.
- SurveySubmission — portable URL artifact sent to the administrator.
- SurveyGroup — relates multiple survey instances/submissions.

Core deterministic rule:

Immutable Published Template
+
Survey Submission URL
=
Complete Reproducible Survey Result

No respondent-side hidden state should be required.

14. Evaluation Order

Recommended conceptual order:

1. Parse submission envelope
2. Resolve template
3. Verify template fingerprint
4. Verify submission integrity
5. Decode primitive answers
6. Validate answer cardinality
7. Determine applicability
8. Calculate prerequisite derived facts
9. Run validation
10. Calculate completion state
11. Calculate question scores
12. Calculate section scores
13. Calculate survey result
14. Calculate group result if context exists
15. Calculate remaining derived facts
16. Trigger recommendations/actions
17. Produce SurveyResult

Implementation may optimize this, but dependency behavior must remain deterministic.

The fingerprint length should be chosen deliberately based on collision risk, number of templates, URL budget, and expected system lifetime.

20. Answer Encoding

Answers should be bit-packed based on template-defined cardinality.

Examples:

Boolean          -> 1 bit
Ordinal(3)       -> 2 bits
Ordinal(5)       -> 3 bits
Ordinal(7)       -> 3 bits
Bounded 0..10    -> 4 bits
Choice(8)        -> 3 bits
MultiChoice(6)   -> 6-bit mask

The published template defines a deterministic response layout.

21. Special-State Encoding

For a 5-value ordinal, one possible encoding is:

0..4 = actual answer
5 = N/A
6 = Don't Know
7 = Unanswered

This fits in three bits.

But the encoder should be optimized across the whole survey. Separate presence/special-state bitmaps may be more efficient when many questions support the same special states.

The decision should be based on measured survey payloads, not intuition.

22. Multi-Select, Ranking, and Allocation

Multi-select should normally use bitmasks.

Ranking may later use compact permutation encoding such as factoradic/Lehmer coding or bounded Top-N representation.

Allocation uses bounded integer values based on the template's fixed total and choice count, with validation enforcing the total.

23. URL-Safe Serialization

After binary packing, encode the payload using a URL-safe representation.

Candidates:

Base64url
Base32
Custom alphabet

Base64url is the likely first default because it is compact and widely supported.

24. Response Encoding Version

Every submission explicitly identifies the encoding format version.

ResponseEncodingVersion = 1

This permits future changes to bit layout, compression, special-state representation, envelope structure, and integrity algorithms without breaking old submissions.

25. Integrity and Authenticity

Every submission should support corruption detection.

Possible integrity mechanisms:

CRC32
Truncated cryptographic hash

Integrity detects truncation, malformed copying, and accidental corruption.

Authenticity is a separate concern.

Possible policies:

None
IntegrityOnly
Signed

If signed submissions are needed, HMAC or another keyed signature can be used. Signing should only be required where it provides actual business value.

26. URL Size Budget

Do not design to theoretical browser maximums.

Establish a conservative supported URL budget through real testing, including:

- Safari on iPhone
- Safari on macOS
- Chrome
- Edge
- Email clients
- SMS/iMessage
- Slack/Teams-style messaging
- Copy/paste workflows
- QR codes if planned

Benchmark realistic surveys:

25 questions
50 questions
100 questions
200 questions

with combinations of Boolean, Likert 5, Likert 7, single choice, multi-select, N/A, and Don't Know.

Record:

Raw bits
Encoded bytes
URL characters
Header overhead
Integrity overhead

- Explicit confidence questions

    | DontKnow
    | Answered of AnswerValue

    | HigherIsBetter
    | HigherIsWorse
    | Neutral

    | Scalar
    | Categorical
    | Profile
    | Composite

    | Draft
    | Validated
    | Published
    | Superseded

This aligns with the explicit-state architecture and makes illegal combinations harder to represent.

38. Reporting Boundary

Reporting must not determine:

- Whether a question applies
- Whether an answer is valid
- How a question scores
- How a section scores
- Which maturity level applies
- Which recommendations trigger
- Whether the survey is complete

Those are engine responsibilities.

Reporting should decide:

- What to display
- How to organize it
- Audience-specific views
- Visual presentation
- Export format

41. Core Invariants

1. Published templates are immutable.
2. Every published template has a deterministic hash.
3. Any semantic template change creates a new version.
4. Old published versions remain resolvable.
5. A submission identifies the exact template needed to interpret it.
6. The URL contains all non-reconstructable respondent state.
7. The template owns meaning; the submission owns state.
8. Decoding never depends on mutable external configuration.
9. Unsupported versions/features fail explicitly.
10. Special answer states remain semantically distinct.
11. Validation is separate from scoring.
12. Flow is deterministic.
13. Derived facts are deterministic.
14. Rule dependencies are cycle-free.
15. Section scoring is first-class.
16. Survey-level scoring is first-class.
17. Group-level scoring is optional but supported.
18. Result shape is not assumed to be a single number.
19. Recommendations are engine outputs.
20. Reporting consumes engine results rather than recreating business logic.
21. The same template, instance context, and answers always produce the same result.
22. URL corruption is detectable.
23. Response encoding is explicitly versioned.
24. Published templates contain or immutably reference everything required for interpretation.
25. Every valid answer state is representable by the encoding contract.

42. Canonical Architectural Principle

The survey system should behave like a small deterministic interpreter.

Immutable Template = program
Submission URL     = input state
Survey Engine      = interpreter
SurveyResult       = deterministic output

Execution:

Template
    +
Submission
    ↓
Decode
    ↓
Validate
    ↓
Evaluate
    ↓
Score
    ↓
Classify
    ↓
Recommend
    ↓
SurveyResult

This architecture keeps the engine compact, testable, explainable, version-safe, and well suited to F# WebAssembly.
